Visión general del sistema

El Digesto UNSL es una aplicación React de página única (SPA) que digitaliza el acceso al digesto administrativo de la Universidad Nacional de San Luis. Tres módulos principales —Alta, Búsqueda y Novedades— comparten un único archivo de datos simulados (mock) que actúa como sustituto temporal de una API real.

¿Por qué un mock unificado?
Antes de esta refactorización, cada módulo tenía sus propios datos hardcodeados dentro del componente JSX o en archivos JSON separados con esquemas distintos. Al centralizar todo en src/data/normativas.mock.json, cualquier cambio en los datos se refleja simultáneamente en los tres módulos, eliminando duplicaciones y posibles inconsistencias.

La arquitectura sigue el patrón JSON → Servicio → Componente: el JSON es la fuente de verdad, los servicios (src/services/) normalizan y filtran los datos con lógica reutilizable, y los componentes React consumen esos servicios mediante useEffect.

4

Capa de servicios

Los servicios son módulos JavaScript en src/services/ que encapsulan toda la lógica de acceso y transformación de datos. Los componentes nunca tocan el JSON directamente.

Patrón "simularRespuesta": Todas las funciones públicas (prefijo obtener o buscar) devuelven una Promise con un delay de 100–200 ms. Esto imita el comportamiento de una API real y permite migrar a fetch() en el futuro sin cambiar el código de los componentes.

4.1 services/novedades.js

Función exportadaParámetrosRetorno
listarTipos() — Array de strings con los tipos únicos del mock
filtrarNovedades(tipo, query) tipo: string, query: string Array de normativas filtradas y mapeadas al shape de Novedades.jsx
obtenerNovedades(tipo, query) tipo: string, query: string Promise<Array> — versión asíncrona

Transformación de datos realizada por el servicio:

  • Renombra titulo → title (shape del componente)
  • Convierte fecha ISO a texto legible: "2026-09-18" → "18 de Septiembre de 2026"
  • Agrega campo pdfUrl: '#' (placeholder)
  • Ordena por fecha descendente (más recientes primero)

4.2 services/busqueda.js

Función exportadaParámetrosRetorno
filtrarResultados(params) Objeto con 7 filtros (ver abajo) Array de normativas filtradas y mapeadas al shape de Busqueda.jsx
buscarNormativas(params) Mismo objeto de filtros Promise<Array> — versión asíncrona

Parámetros de filtrado disponibles:

ParámetroTipoDescripción
searchTermstringTexto libre: busca en título, snippet y código
tipoDocumentostringFiltra por tipo (ej: "resolucion")
organismoEmisorstringFiltra buscando el texto en origen y organo
numeroNormastringBusca el número dentro del campo codigo
anioNormastringCompara los 2 últimos dígitos del año con el sufijo del código

fechaHastaISO dateFiltro de rango máximo

Transformación de datos realizada por el servicio:

  • Renombra titulo → title
  • Usa origen como campo organo visible (más descriptivo para búsqueda)
  • Convierte fecha de YYYY-MM-DD a DD-MM-YYYY
  • Ordena resultados por fecha descendente
5

Módulo Novedades

Muestra cronológicamente las últimas normativas registradas con filtros por tipo y búsqueda de texto.

normativas.mock.json
datos crudos
→
services/novedades.js
obtenerNovedades(tipo, query)
filtra + mapea + ordena
→
Novedades.jsx
useEffect → setNovedades
renderiza cards

Lógica del componente

// Cada vez que cambia filterTipo o searchQuery, se recarga desde el servicio
useEffect(() => {
  obtenerNovedades(filterTipo, searchQuery).then(setNovedades)
}, [filterTipo, searchQuery])

El filtrado ocurre en el servicio (no en el componente). El componente simplemente muestra novedades tal como llegan de la Promise.

6

Módulo Búsqueda

Permite buscar normativas mediante texto libre y múltiples filtros avanzados. La búsqueda se ejecuta al presionar el botón "Buscar" (submit del formulario).

normativas.mock.json
datos crudos
→
services/busqueda.js
buscarNormativas(params)
7 filtros aplicados
→
Busqueda.jsx
setResults(data)
renderiza resultados

Lógica del componente

const handleSearch = (e) => {
  e.preventDefault()
  buscarNormativas({
    searchTerm, tipoDocumento, organismoEmisor,
    numeroNorma, anioNorma, fechaDesde, fechaHasta,
  }).then((data) => {
    setResults(data)
    setHasSearched(true)
  })
}
Estado inicial: La sección de resultados no aparece hasta que el usuario hace una primera búsqueda (hasSearched === false). Si la búsqueda no arroja resultados, se muestra un mensaje vacío en lugar de una lista.
7

Módulo Alta de Documentos

Panel de administración que permite registrar, editar y eliminar normativas. Tiene dos pestañas: Panel de Gestión (tabla) y Cargar Nuevo Documento (formulario).

Fuente de datos inicial

AltaDocumento.jsx importa el mock unificado y lo adapta al shape de TablaGestion: 

const documentosIniciales = mockData.normativas.map((n) => ({
  id:          n.id,
  fecha:       n.fechaAlta,   ← timestamp legible para la tabla
  tipo:        n.tipo,
  origen:      n.origen,
  organo:      n.organo,
  descripcion: n.descripcion,
  pdfNombre:   n.pdfNombre,
}))

Persistencia con localStorage

Una vez cargados, los documentos se persisten en localStorage bajo la clave digesto_documentos. Al recargar la página, se recuperan del storage; el mock solo se usa como dato inicial si el storage está vacío. 

// Inicialización: localStorage tiene prioridad sobre el mock
const [documentos, setDocumentos] = useState(() => {
  const local = localStorage.getItem('digesto_documentos')
  if (local) return JSON.parse(local)
  return documentosIniciales  ← datos del mock unificado
})

// Persistir en cada cambio
useEffect(() => {
  localStorage.setItem('digesto_documentos', JSON.stringify(documentos))
}, [documentos])

Catálogos del formulario

FormularioAlta.jsx lee los tres arrays de catálogo directamente del mock, eliminando la duplicación de listas hardcodeadas: 

import mockData from '../../../data/normativas.mock.json'

9

Guía para agregar o modificar datos

Agregar una nueva normativa

Solo hay que editar src/data/normativas.mock.json y agregar un objeto al array normativas:

{
  "id": "res-nuevo-2027",        ← slug único, sin espacios
  "codigo": "RR-1-200/27",
  "titulo": "Nombre completo de la norma",
  "tipo": "Resoluciones",          ← debe estar en tiposDocumento[]
  "origen": "Rectorado",
  "organo": "Consejo Superior",
  "descripcion": "Descripción completa...",
  "snippet": "... fragmento para búsqueda ...",
  "fecha": "2027-03-15",            ← formato ISO YYYY-MM-DD
  "fechaAlta": "15/03/2027, 09:00:00",
  "pdfNombre": "Resolucion_RR_200_2027.pdf"
}

Agregar un nuevo tipo de documento

Agregar el valor al array tiposDocumento en el mock. Automáticamente aparecerá en el formulario de Alta y podrá filtrarse en Novedades.

Agregar un nuevo organismo emisor

Agregar el valor a origenesTramite y/o organosEmisores. Los selects del formulario se actualizan automáticamente.

Migrar a una API real

Cuando el backend esté listo, solo hay que reemplazar el cuerpo de las funciones en services/novedades.js y services/busqueda.js:

// Antes (mock)
export function obtenerNovedades(tipo, query) {
  return simularRespuesta(filtrarNovedades(tipo, query))
}

// Después (API real) — los componentes no cambian
export function obtenerNovedades(tipo, query) {
  return fetch(`/api/novedades?tipo=${tipo}&q=${query}`)
    .then((r) => r.json())
}
Ventaja clave: Gracias al patrón de servicios, los componentes React (Novedades.jsx, Busqueda.jsx) no necesitan modificarse al migrar al backend real. Solo se actualizan los archivos en src/services/.
